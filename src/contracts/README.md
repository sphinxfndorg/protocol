# Sphinx programmable contracts

Contracts are normal signed transactions committed by consensus. Contract code,
metadata, and storage are included in `StateDB` and therefore in each block's
state root.

## Native SIP-20 token

Deploy a token by placing the JSON generated by `BuildDeployCode` in
`Transaction.Code`. A deploy has no `ToContract` or `CallData`.

```go
code, _ := contracts.BuildDeployCode(&contracts.DeploySpec{
    Runtime: "native", Standard: "sip20", Name: "Example", Symbol: "EXP",
    Decimals: 18, InitialSupply: "1000000000000000000",
})
```

The contract address is deterministic:
`sha256(sender || nonce || sha256(code))`, rendered as an `sc...` address.

Call the deployed address using `ToContract` and JSON made by `BuildCallData`.
SIP-20 supports `mint`, `transfer`, `balance_of`, and `info`.

## Native SIP-721 collection

Deploy a collection with `Runtime: "native", Standard: "sip721"`. The deployer
becomes the collection owner and the only minter. `mint(to, token_uri,
mint_id, royalty_bps, usage_fee, royalty_recipient)` allocates an
Ethereum-style incrementing `token_id` and records `ownerOf`/`tokenURI` in
contract storage. `transfer_from` and `approve` follow ERC-721 approvals.
Reads: `owner_of`, `token_uri`, `token_id_of_mint`, `info`.

### Embedded economics

A token's terms are frozen at mint and enforced by every node at consensus —
no wallet, marketplace, or indexer is trusted to report them:

- `royalty_bps` (0..10000) — resale royalty. Each value-carrying
  `transfer_from` sale splits the price the buyer's transaction escrows at the
  contract (`tx.Amount`): `max(amount, policy.MinTokenSaleValue) ×
  royalty_bps/10000` (capped at the escrow) goes to the creator forever, the
  remainder to the seller. Sale flow: the seller `approve`s a buyer, and the
  buyer signs the purchase. There is deliberately no unapproved force-purchase
  path.
- `usage_fee` (decimal nSPX) — per licensed-access micro-fee.
  `purchase_license` requires the transaction to carry exactly the posted fee,
  forwards it to the creator, and records a single active licensee
  (`sip721:token:<id>:licensee`). `revoke_license` is limited to the creator
  or collection owner. This enforces payment + entitlement — the license
  receipt — not a bytes-gate over off-chain IPFS reads.
- `royalty_recipient` — optional payout override; defaults to the creator (the
  collection owner at mint).
- `terms_of` reads a token's frozen terms and current licensee for
  marketplaces and indexers.

Terms are immutable: there is deliberately no `set_terms`, so the current
owner can never rewrite the economics of a token someone already bought or
listed. The same terms are committed in the mint-anchor `AnchorTag` at the
receipt layer (`core.ValidateAnchorData`), making the creator's value model
verifiably pre-announced for every participant.

## SVM1 bytecode

SVM1 is a bounded deterministic runtime for simple applications. A program
starts with the four bytes `SVM1`, then uses only the exported opcodes in
`svm.go`: `SVMPush8`, integer arithmetic, `SVMStore`, `SVMLoad`,
`SVMCallDataWord`, and a final
`SVMStop` or `SVMReturn`. It has no loops, calls, wall clock, randomness,
network access, floating point, or filesystem access.

`SVMCallDataWord` pops a byte offset and pushes the next eight bytes of the
transaction's `CallData` as a zero-padded big-endian unsigned integer. This is
the deterministic input mechanism for parameterized SVM contract calls.

This intentionally small first runtime lets all nodes exactly precompute gas
before admission. Each operation, code byte, and call-data byte is charged by
the active `policy.PolicyParameters` schedule.

## RPC reads

`getcontract(address)` returns metadata and code (hex).
`getcontractstorage(address, key)` returns a storage value as hex.

Contract deploys and calls are submitted through `sendrawtransaction` like a
native transfer. Core validates gas and executes them; clients must never
consider a local execution authoritative.

## WASM contracts (Rust, C/C++, TinyGo, AssemblyScript)

WASM bytecode is also accepted as deployment `Code` when it is a standard
WASM 1.0 binary and exports a no-argument function named `sphinx_main`.
The interpreter is pinned by the Go module and policy caps bytecode at 512 KiB
and memory at 16 pages (1 MiB).

The only supported import module is `sphinx`:

| Import | Signature | Meaning |
| --- | --- | --- |
| `storage_get` | `(u64 key) -> u64` | Read a persistent storage word. |
| `storage_set` | `(u64 key, u64 value)` | Write a persistent storage word. |
| `calldata_word` | `(u64 byte_offset) -> u64` | Read an 8-byte, big-endian, zero-padded call-data word. |
| `caller` | `() -> u64` | First 64 bits of SHA-256 of the caller address. |
| `transferred_value` | `() -> u64` | nSPX attached to the call (values above `u64` are rejected by the ABI boundary). |
| `block_height` | `() -> u64` | Current block height. |
| `emit_event` | `(u64 topic, u64 value)` | Commit an immutable, transaction-scoped event. |
| `transfer` | `(i32 address_ptr, i32 address_len, u64 nspx) -> i32` | Transfer from the contract balance; returns `0` on success. |

WASI is deliberately unavailable. There is no filesystem, networking, host
clock, randomness, process environment, or thread API. Use
`abi.NewWASMDeployTx` and `abi.NewWASMCallTx` to create unsigned transactions.

### Function arguments

For conventional WASM contracts, use `abi.NewWASMFunctionCallTx`. It encodes
an 8-byte SHA-256-derived function selector followed by big-endian `u64`
arguments. In a contract, read selector with `calldata_word(0)`, then arguments
at byte offsets `8`, `16`, etc. `abi.EncodeWASMFunctionCall`,
`DecodeWASMFunctionCall`, and `WASMFunctionSelector` are available to SDKs and
tests that need the same binary layout without constructing a transaction.

For artifact transport, use `abi.NewBinaryArtifact("wasm1", code)`. It emits
canonical `0x` hexadecimal code plus a SHA-256 content hash. `bind` also
provides `LoadContractBinary`, `BuildWASMDeploymentTxFromFile`, and
`EncodeRawTransaction` for compiler output and node wire payloads.

The accepted profile is deliberately bounded: floating point, loops, internal
or indirect calls, memory growth, bulk-memory, and SIMD instructions are
rejected. Every accepted instruction and every statically known storage/event
host call is charged by active policy before execution. This makes one
invocation bounded without relying on a wall-clock timeout.
